# 多租户智能体办公平台（共享资源池版）设计决策记录

> 本文档由烤问式对齐过程产出，每条决策均已在对话中由需求方拍板。配套设计文档：[workbuddy-pool-design.md](workbuddy-pool-design.md)。

## D1 · 池化对象：引擎进程与执行环境两层都池化
- **问题**：稀缺资源到底是"对话引擎进程"还是"工具执行环境（沙箱）"，还是两者？
- **结论**：两者都池化。引擎侧多租户共享进程，执行侧 K8s 沙箱池按需绑定、空闲回收。
- **理由**：老 OpenClaw 方案的成本大头是每用户一个常驻 Pod；只池化一层都拿不到量级提升。
- **影响章节**：1.1、2.1

## D2 · 引擎层隔离边界：进程内多租户
- **问题**：多用户能否共用同一引擎进程（合租），还是必须进程级隔离（每人一个实例、用完回收）？
- **结论**：进程内多租户。一个引擎进程同时服务多个用户，靠会话级作用域与配置隔离。
- **理由**：进程级隔离只是给老模式换回收策略，经济性大头拿不到；安全隔离放在执行环境层（每用户独立沙箱），用户代码实际运行的地方才需要强隔离。
- **影响章节**：2.1、3.1
- **已知风险**：单进程故障影响面为该片所有在线用户；靠多副本与秒级会话换机缓解。

## D3 · "人走活不停"的范围：只支持 AI 任务服务端续跑
- **问题**：用户关闭页面后，什么东西要继续活着？
- **结论**：只支持"AI 任务在服务端跑完，结果记入会话存档"。用户自己起的长期运行程序（7×24 服务、定时脚本）不支持；将来若有需求，做成显式的"后台任务"独立功能，单独配额与计费。
- **理由**：续跑 AI 任务在本架构中几乎免费（大脑在服务端、存档在数据库）；而保活用户程序要求沙箱永不回收，直接摧毁池化经济性，且只是少数需求。
- **影响章节**：1.2（范围内/外）、2.3、3.2（回收条件）

## D4 · 沙箱回收时机：任务完成且页面关闭后保温 10~15 分钟
- **问题**：AI 活干完、用户也走了之后，沙箱留多久再回收？
- **结论**：保温 10~15 分钟，时长做成配置项，POC 阶段用真实数据调优。回收只收沙箱；用户文件（CFS）与会话存档（数据库）永久保留。
- **理由**：覆盖"离开一小会儿就回来"的高频场景（秒开体验）；超时场景回收后回来只是冷启动几秒，不是丢东西。
- **影响章节**：2.3、3.2

## D5 · 规模估算口径
- **问题**：池子建多大、按什么数字设计？
- **结论**：目标态 30 万员工，并发率按 5% 估算（约 1.5 万并发对话）；现有预算 1000 实例 × 2~3C ≈ 2500C 起步。任务画像：办公场景（文档进、PPT 出），单任务 1~2 分钟为主，几十分钟的长任务少。
- **理由**：资源占用只与"同时进行的对话数"相关，与注册数无关；2500C 按沙箱 0.5C/个估算可扛约 5000 并发，即同等预算支撑约 10 万注册用户，为老模式的 100 倍。
- **影响章节**：1.1、1.3、3.5

## D6 · 模型来源：POC 用 DeepSeek 官方 API，落地换私有化网关
- **问题**：模型调外部 API 还是企业内部私有化模型？
- **结论**：POC 调 DeepSeek 官方 API；落地时企业私有化部署 DeepSeek V4 Flash（兼容 OpenAI 协议），只改网关地址配置。
- **理由**：DeepSeek Harness 原生支持 DeepSeek；私有化模型兼容 OpenAI 协议，模型层不挡路。合规切换是纯配置工作。
- **影响章节**：1.2、2.1

## D7 · POC 身份体系：模拟多用户
- **问题**：POC 接不接企业自研统一认证？
- **结论**：不接。POC 用模拟身份（请求头携带用户标识），只要能自动化模拟多用户并发登录压测即可；落地阶段再对接企业自研 SSO。
- **理由**：POC 的核心命题是证明资源模型，不是登录正规性；但"用户身份"管道（会话归属、文件隔离、用量归属）必须在 POC 就真实贯通。
- **影响章节**：1.2、2.2、3.1

## D8 · 大脑无状态：会话存档共享数据库，任意大脑可唤醒任何会话
- **问题**：会话状态放哪？大脑进程是否有状态？
- **结论**：会话存档放共享数据库（PostgreSQL），任何大脑进程都能唤醒任何用户的会话，路由无需粘连。
- **理由**：大脑层水平扩容、故障换机零成本，是 30 万人目标态的前提；DeepSeek Harness 的会话本就是事件溯源 + 可插拔存档 seam，换共享库只是新增一个 Provider。
- **影响章节**：2.1、3.1、3.4

## D9 · 池管理器独立部署，全局一本账
- **问题**：池管理逻辑做成独立服务，还是作为插件住在每个大脑进程里、经共享数据库协调？
- **结论**：独立小服务（POC 单副本快速重启，落地主备），全局唯一账本；大脑进程里只放一个客户端插件。
- **理由**：池管理的三件后台家务（回收倒计时、预热池补水、宕机收尸）必须"有且只有一个"执行者；分布式住在大脑里需要选主，选主复杂度超过多部署一个轻服务的全部成本，且竞态要到多进程压测时才暴露。全局水位指标也从单一口子出。
- **影响章节**：2.1、3.2

## D10 · 沙箱按人绑定，绑定键设计为可配置
- **问题**：沙箱绑给"用户"还是绑给"一次对话"？
- **结论**：按人绑定——同一用户同一时刻至多一个沙箱，多个对话共用。池管理器账本的主键是抽象的"绑定键"字段（当前取值 = 用户 ID），不写死。
- **理由**：符合"我的机器"心智、省资源、回收判定简单；将来若要改成按对话绑，只需把绑定键换成"用户 ID + 对话 ID"，池管理器与存储层零改动，代价仅是池容量重估。
- **影响章节**：2.3、3.2、3.3

## D11 · 用户文件存储：企业现有 CFS，按用户目录隔离
- **问题**：用户上传的文档与生成结果存哪？
- **结论**：沿用企业现有腾讯云 CFS（私有化部署版），每用户一个专属目录，沙箱启动时挂载所属用户的目录；沿用现 OpenClaw 的 Web 上传做法。
- **理由**：企业已有现成设施与运维经验，存储层零新工作；按目录隔离 + 权限控制即可满足用户间不可见。
- **影响章节**：2.1、3.3

## D12 · 前端 UI 复用 dsh client 插件树，不独立开发
- **问题**：多用户共享资源池形态下，用户打开网页看到的客户端（聊天、会话列表、文件上传、事件进度流）是要传统方式独立开发一套前端，还是复用 dsh 的 plugin/UI 机制？
- **结论**：复用 dsh 的 client 插件树，不独立开发。dsh 的浏览器 GUI 本身就是「第二个 cordis 插件树」：`packages/client/**` 的每个 `ui-*` 包都是自带 UI 的插件，经 slot 组装界面，宿主按 manifest 以 `GET /plugins/<id>/client.js` 按需分发 bundle，`apps/web` 只是薄薄 Vite 壳。**UI 骨架插件零改动**，多租户带来的新界面以**新增 UI 插件**挂进现有 slot。
- **理由**：dsh 的「everything is a plugin」不只包后端能力，前端 GUI 正是插件组装的一等公民设计与实现。把前端另起炉灶会同时丢掉「装插件拼工作台」的分发与扩展机制，是在已经存在的 Client 插件树旁再造一个平行前端。
- **分工边界**：UI 插件机制解决「界面怎么组合」，不解决「谁是谁」；「多租户」落在宿主侧，由本方案新增（`packages/tenant/`）。dsh 现有 `identity` 仅为匿名非认证关联 ID、`ctx.sessions.list()` 全局无归属、会话标头无租户字段，三者均为新增面。
- **警觉点**：「插件树全局一份（composition）」与「会话按用户隔离（tenancy）」必须分两层，per-session 状态不得漏进全局插件树。
- **三种 plugin 形态均为第一等公民**：多租户方案必须同时继续支持 ① 纯前端 plugin（仅 client 半的 UI 插件）、② 前后端都有的 plugin（同包两半各归其位、经 manifest 粘合）、③ 纯后端 plugin（仅 host 半的能力/seam 插件）。①②的验收以「完整多用户 UI」为用户感知级判据——对应 design 文档 1.3 的 V 组（V1/V2/V3）。
- **影响章节**：2.1、2.4、1.3（V 组验收）
